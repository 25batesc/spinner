# Audit: the Spinner docs against Brooks and ASD-STE100

Date: 2026-10-26. Scope: `README.md`, `docs/*.md`, `sessions/*/MISSION.md`, `sessions/*/RUN.md`, `sessions/*/agents/*/BRIEF.md` (13 files, 645 sentences). Two lenses:

1. **Fred Brooks, *The Mythical Man-Month*** (1975; 20th-anniversary edition 1995). Not a method in the step-by-step sense. A set of propositions about how software projects fail and what documents and roles keep them honest. Each chapter below is a check.
2. **ASD-STE100 Simplified Technical English**, Issue 9 (January 2025): 53 writing rules and a dictionary of about 900 approved words. STE is for procedures and descriptions that someone must follow exactly. Spinner has such text: the briefs, the run sheets, the protocol rules, and soon the system-prompt sections and tool descriptions that agents read every turn. Those are the texts where STE pays off. The README is marketing-adjacent prose; it gets the lighter treatment.

Metrics come from `tools/doc-metrics.py` (added with this audit; run `python3 tools/doc-metrics.py` from the repo root). This is a self-assessment. No STE checker software was used, and the STEMG does not certify checkers anyway.

Verdict: **the structure is Brooks-shaped: a workbook, a manual, sharp milestones, a pilot first. Three of his six documents are missing: budget, schedule with dates, organization. Several words carry two meanings. The agent-facing texts read like essays, not procedures.**

### Where the design agrees with Brooks without trying

The session directory is a project workbook. `MISSION.md`'s human-owned sections are the architect's spec; the Contracts section is the "formal definition beside the prose". Ownership by path is Brooks' partitioning. M0-by-hand is the pilot system. The stage table with `needs_human` is a milestone chart at feature granularity. Keep all of it.

### Where it disagrees, and should say so

Spinner's thesis, several agents on one feature, runs against Brooks' Law. The honest framing: the agents do not make a single feature faster by number; they let *you* run four features at once because the doc, not you, carries the communication. Write that sentence into README. It also tells you when to stop adding agents to a session.

### 2.3 Findings by rule

**Sentence length.** 15% of sentences are over the limit. The worst are in ARCHITECTURE ("Why pi first", 95 words; "This solves three things at once", 59) and the README opener (64). In the briefs, the board brief has a 49-word sentence that packs four instructions.

**One instruction per sentence.** The briefs chain instructions with semicolons. Example, stack brief:

> Postgres: one shared `spinner-postgres` container; `spinner seed rebuild` builds the template DB; `up` runs `CREATE DATABASE …` (make sure nothing is connected to the template); `close` drops it.

That is four instructions and a warning in one line. STE wants five sentences, warning first.

**Verb forms.** About 100 "-ing" forms outside technical names ("editing", "polling", "bucketing", "showing", "summarising"). STE allows "-ing" only in technical nouns. Stage names (*fixing*, *approving*, *addressing*, *verifying*) are technical names and may stay, but they must then always appear as names (code font or italics), never as verbs in running text.

**Active voice.** 58 passive constructions. Most hide the actor that matters: "Threads are bucketed by first-comment author" (who buckets? the tracker). "The brief is injected into the agent's system prompt" (by the daemon, through the extension). In the protocol, the actor is the whole point: it decides who may write what.

**One word, one meaning.** This is the serious one. Four words carry two or more meanings across the docs:

| Word | Meanings found | Count | Proposal |
|---|---|---|---|
| **board** | (a) the `## Board` section of MISSION.md, the per-agent row table; (b) the pipeline board of sessions | 17 / 38 | Rename the MISSION section to **`## Roster`** ("Roster row", `mission_roster` tool). "Board" means only the pipeline board |
| **review** | Devin Review; peer review; the `spinner review` command; the `review/` directory; review threads; the `review.*` config | 55 | `spinner review` → **`spinner post`** (it posts to Slack). `review/` → **`threads/`**. `review_*` tools → `thread_*`. Config `review.*` → `threads.*`. "Review" then means only what GitHub calls a review |
| **state / status / stage** | `state` for PRs, stack, agents, and the Board column; `status` in `STATUS.md` and `spinner status`; `stage` for the pipeline | 18 / 4 / 34 | `stage` = pipeline only. `state` = daemon-observed facts (PR, stack service). Agent process → `process`. Agent self-report → the Roster column, named **Doing** and **Blocked?** instead of "State" |
| **human / you / Cullen / operator** | the person orchestrating, addressed three ways | 45 / 55 / 22 | Define **operator** once as the technical name; write **you** in docs; **Cullen** only inside session files |

Also: "stack" vs "environment" (46 / 2) → keep *stack*, delete *environment*. "preview", "preview pane", "preview window" → *preview* is the thing, *preview pane* is the UI region; never "window".

**Unapproved words** (STE dictionary): *via* (8) → "through"; *whether* (7) → "if"; *may* (2) → "can" or "is permitted"; *should* (1) → "must"; *prefer*, *simply*, *therefore*, *as well as*. Low effort, do it in the briefs first.

**Do not omit parts of the sentence.** Table cells and the command list are telegraphic ("polls GitHub; notifies when the bot posts"). Acceptable in tables if every cell follows the same pattern; fix the ones that mix fragments with full sentences.

**Vertical lists.** Several sentences carry inline lists of 4–6 items in parentheses. Convert to lists, especially in the protocol's command descriptions.

**Safety instructions.** The docs already start prohibitions with the command ("Never force-push…", "The daemon never posts to Slack…"). STE would say "Do not" rather than "never". Minor.

### 2.4 A conformant rewrite (stack brief, Engineering section)

Before (one line, 4 instructions):

> Postgres: one shared `spinner-postgres` container; `spinner seed rebuild` builds the template DB; `up` runs `CREATE DATABASE spinner_<id> TEMPLATE <template>` (make sure nothing is connected to the template); `close` drops it.

After:

> **Database**
> 1. Use one shared Postgres container named `spinner-postgres` for all sessions.
> 2. Make `spinner seed rebuild` create the template database.
> 3. Make `spinner up` run `CREATE DATABASE spinner_<id> TEMPLATE <template>`.
> 4. Before step 3, make sure that no client is connected to the template database. Postgres refuses the clone if one is.
> 5. Make `spinner close` drop the session database.

Every sentence is under 20 words, imperative, active, one instruction. The warning stands alone and comes before the step it protects. This is the pattern for all five briefs and for the extension's system-prompt sections.

### 2.5 Proposed house rules (a Spinner subset of STE)

Ten rules, for `docs/WRITING.md`, enforced on briefs and protocol text by `tools/doc-metrics.py` in CI:

1. Procedures: 20 words per sentence. Descriptions: 25. The tool fails the build on a longer sentence in a brief or run sheet.
2. One instruction per sentence. No semicolon chains in a brief.
3. Imperative for instructions ("Read…", "Update…"). Simple present for descriptions. No "-ing" verbs.
4. Active voice. Name the actor: the daemon, the extension, the agent, you.
5. One word, one meaning. The glossary below is the dictionary. New terms go in the glossary before they go in a doc.
6. No synonyms for defined terms. Not "env", "environment", "sandbox" for *stack*.
7. Vertical lists for more than three items.
8. Warnings before the step, as a separate sentence starting with "Do not" or "Make sure".
9. No *via, whether, may, should, prior to, in order to, leverage, as well as*.
10. Articles stay in ("the daemon", not "daemon").

Glossary, the controlled dictionary, first cut. One meaning each:

- **agent**: one coding-agent process attached to a session.
- **board**: the pipeline board, all sessions with their stage. Not the roster.
- **brief**: `BRIEF.md`, what one agent owns and must do.
- **fixer**: the agent role that works through review threads.
- **inbox**: the message directory of a session.
- **mission doc**: `MISSION.md`.
- **operator**: the person who runs the sessions. In docs, "you".
- **pipeline**: the stages from *building* to *merged*.
- **preview**: a running service of the session, as shown in a **preview pane**.
- **roster**: the per-agent table in the mission doc. Formerly "Board".
- **session**, **session directory**: the unit of work and its directory.
- **stack**: the repos and services that run together for a session. Not "environment".
- **stage**: the pipeline position of a session. Not "status", not "state".
- **thread**: a GitHub review thread.
- **verify**: the operator's local-test tick.
- **worktree**: a git worktree of one repo inside a session.
