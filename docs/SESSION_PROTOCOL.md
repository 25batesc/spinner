# Session protocol

This is the contract everything else in Spinner is built against. The CLI writes it, the daemon watches it, the UI renders it, and agents read and update it every turn. It is deliberately **plain files**, so it works before any Spinner code exists (see [examples/sessions/s001-bootstrap](../examples/sessions/s001-bootstrap/MISSION.md)) and stays readable with `cat`.

Terms in this document have one meaning each; see the glossary in [WRITING.md](WRITING.md). The **operator** is the person who runs the sessions. In the briefs, the operator is named.

Design rules:

1. A person can read the whole session state from one directory with no tooling.
2. An agent gets everything it needs to coordinate from one file (`MISSION.md`) that fits comfortably in context (target < 400 lines).
3. Machine state and shared narrative are separate files with separate owners, so nobody clobbers anybody.
4. Nothing in the session directory is ever committed to a work repo.
5. A session has at most **three agents**. If a feature needs more, split it into two sessions. (Communication paths grow with the square of the agent count; the mission doc keeps them linear only while the count is small.)
6. `session.yaml` carries a `version`. The daemon reads every version from 1 upward and migrates older files forward in place. The pi extension states the version it expects and refuses a newer one.

## Where everything lives

All of Spinner's state is plain files under `~/.spinner/`. There is no database. The daemon rebuilds what it knows by reading this tree at start.

```
~/.spinner/
├── config.yaml           # your settings: default harness, GitHub/Slack/pipeline config, notifications
├── projects/
│   └── acme/spinner.yaml # a private stack spec (multi-repo projects; see STACK_SPEC.md)
├── seeds/                # template-database metadata and dumps
├── sessions/
│   └── s17-refund-flow/  # one live session, layout below
└── archive/              # closed sessions, moved here by `spinner close`
```

Rules:

- `~/.spinner/` is never inside a git repository. `spinner doctor` checks this and refuses to create sessions otherwise.
- A work repo never contains session state. Each worktree gets a `.spinner` symlink back to its session directory, and the daemon adds `.spinner` to that repo's `.git/info/exclude`, which is per-clone and never committed. Agents reach the mission through `.spinner/MISSION.md`.
- Secrets stay out of files Spinner writes. Provider keys live in the harness's own store (`~/.pi/agent/auth.json` for pi); a Slack token comes from the environment; `config.yaml` holds channel ids and logins, nothing secret.
- A Spinner checkout keeps private stack specs in `local/` (gitignored) and example sessions in `examples/sessions/`, which are templates: `spinner new --from examples/sessions/s002-board-and-stack` copies one into `~/.spinner/sessions/`.

## Session directory layout

```
~/.spinner/sessions/s17-refund-flow/

│                         #   Picked up by every harness that reads context files from parent directories.

│   │   ├── NOTES.md      # written by this agent only. Expands its Roster row.
│   │   └── pi/           # pi --session-dir: transcripts (JSONL), resumable.
│   └── admin-ui/
├── skills/               # session-only skills, loaded in addition to your user and project skills
├── worktrees/
│   ├── backend/          # git worktree of the backend repo on feat/refund-flow
│   ├── admin/
│   └── web/

│   └── .env              # ports, hostnames, DB name, secrets refs

├── threads/              # open review threads per PR, rendered by spinnerd from GitHub
│   ├── backend-412.md    #   bot and human comments with ids, for the fixer agent
│   └── admin-98.md

```

## Context chain

Harnesses read instruction files from the agent's working directory and its parent directories; pi reads `AGENTS.md` (or `CLAUDE.md`) from its agent directory, the working directory and every parent. Because worktrees live inside the session directory, an agent whose cwd is `worktrees/backend/src/refunds/` sees this chain, in load order:

1. `~/.pi/agent/AGENTS.md`: your user-level instructions (pi only).
2. `~/.spinner/sessions/s17-refund-flow/AGENTS.md`: the session file that Spinner generates.
3. `worktrees/backend/AGENTS.md`: the repo's own instructions, tracked in git.
4. `worktrees/backend/src/refunds/AGENTS.md`, if present: the most specific one.

The session file is how Spinner injects the mission into **any** harness without a plugin. The pi extension adds the richer parts on top (tools, per-turn mission refresh). Spinner's UI shows this chain per agent, as a *Context* tab: each file, its scope (user, session, repo, directory), and whether git tracks it. Every file in the chain is editable there. An edit to a repo-level file is a change to the branch and shows up in the diff; an edit to the session file or a user file is not. After an edit, the daemon reloads the agent's context before its next turn (restarting the pi process between turns if the harness has no reload; pi resumes the same session by id).

Skills follow the same idea. pi loads your user skills from `~/.pi/agent/skills/`, project skills from the repo's `.pi/skills/` (after project trust, which Spinner grants when `harness.pi.trust_projects` is on), and session skills from `skills/` through `--skill`. The *Context* tab lists the skills, prompt templates and extension commands an agent has loaded, with their paths, from pi's `get_commands` RPC call.

## `session.yaml`

Owned by `spinnerd`. Agents and the operator read it; only the daemon writes it. (Before the daemon exists, the operator maintains it by hand; the bootstrap session shows a minimal one.)

```yaml

id: s17
slug: refund-flow
title: "Payments: refund flow"
created: 2026-10-20T11:40:00-04:00
stage: fixing               # derived, see "Pipeline stages" below
needs_human: null           # or the single next action: "verify locally", "approve backend#412", "T3 on backend#412 flagged"
branch: feat/refund-flow    # same name in every repo that changes

repos:
  backend:
    path: ~/code/acme-backend
    worktree: worktrees/backend
    changed: true
    pr:
```

## `MISSION.md`

One file, one mission. Every agent reads it in full at the start of every turn (the Spinner pi extension injects it into the system prompt; by hand, the brief tells the agent to read it). The operator reads it to know where things stand without opening any chat.

### Template

```markdown
# s17 · Payments: refund flow

## Goal
Customers can request a refund from the order page; admins approve or reject in
the admin app; approved refunds run through a Temporal workflow that calls Stripe
and updates the order. (One paragraph. Operator-owned.)

## Done when
- [ ] Refund request button on order page (web)
- [ ] Admin refund queue with approve/reject (admin)
- [ ] RefundWorkflow with retry + idempotency (backend)
- [ ] All three PRs green and reviewed

## Plan
- [x] 1. API contract for refunds agreed (backend-api)
- [ ] 2. RefundWorkflow + activities + tests (backend-api)
- [ ] 3. Admin refund queue page (admin-ui)
- [ ] 4. Order page button + request modal (admin-ui, after 3)
- [ ] 5. End-to-end check in the running stack (operator)

## Roster
| Agent       | Owns                          | Doing                             | Blocked?                        | Updated |
|-------------|-------------------------------|-----------------------------------|---------------------------------|---------|
| backend-api | backend/**                    | RefundWorkflow activities + tests | no                              | 11:52   |
| admin-ui    | admin/**, web/**    | RefundQueuePage scaffold          | yes: /refunds does not return 202 yet | 11:50 |

## Contracts & decisions
- 11:48 backend-api: `POST /refunds {orderId, amount}` → `202 {refundId}`; `GET /refunds?status=pending` for the queue. admin-ui: build against this.
- 11:49 operator: use the existing `ApprovalDialog` component in admin, do not add a new one.

## Open questions
- admin-ui: partial refunds in v1, or full amount only?

## Log
- 11:45 backend-api: read mission; starting on contract
- 11:48 backend-api: contract posted, see Contracts
- 11:50 admin-ui: scaffolded RefundQueuePage, blocked on API
- 11:52 backend-api: workflow stub compiles, tests red (expected)
```

### Editing rules

These rules are what make a shared file safe with several writers. They are enforced socially in the bootstrap phase and by the `mission` tool once the daemon exists.

| Section | Who writes | How |
|---|---|---|
| Goal, Done when | Operator | Freely. Agents propose changes under *Open questions*. |
| Plan | Anyone | Add items; every item names one owner; only the owner ticks it. Never renumber. |
| Roster | Each agent, own row only | Overwrite the row. *Doing* is one line, or `done`, or `—` when idle. *Blocked?* is `no` or `yes: <what you wait for>`. |
| Contracts & decisions | Anyone | **Append-only.** To change a contract, add a new entry that says what it supersedes. |
| Open questions | Agents add, operator answers | The operator answers inline or moves the answer to *Contracts*. |
| Log | Anyone | **Append-only**, newest at the bottom, one line: `HH:MM agent: what happened`. |

Conventions:

- Edits are surgical (edit-in-place, never rewrite the file). pi's `edit` tool does a fresh read-then-replace, which is enough with a handful of writers; the daemon serializes writes once it exists.
- When the Log passes ~150 lines the daemon moves the oldest entries to `log/MISSION-<date>.md` and leaves a two-line summary in their place. Agents never prune.
- An agent that edits files **outside its owned paths** logs it first (`11:53 backend-api: touching admin/src/api/client.ts to add the refund method`). Ownership is listed in the Roster and in the agent's `BRIEF.md`.
- Times are local, `HH:MM`. The session's date is in `session.yaml`.

## Agent files

### `agents/<name>/BRIEF.md` (operator-written)

The brief is short and stable. The daemon appends it to the agent's system prompt every turn. Write it as a procedure: numbered steps, one instruction per sentence, at most 20 words per sentence (see [WRITING.md](WRITING.md)).

```markdown
# backend-api

Role: backend engineer for session s17.

## Owns
- `backend/**` (worktree `../worktrees/backend`, branch `feat/refund-flow`).

## Do not edit
- `admin/**` and `web/**`. The admin-ui agent owns them. Send a message if you need a change there.

## Stack
- API: http://api.s17.localhost
- Temporal UI: http://temporal.s17.localhost
- Database: `spinner_s17`, seeded.
- Logs: `spinner logs s17 api`.

## Every turn
1. Read `.spinner/MISSION.md` in full.
2. Update your Roster row when your task or your blocked state changes.
3. Append one Log line when something happens.
4. Put an API change under Contracts before you implement it.

## Finish
1. Make the tests green.
2. Commit on the branch.
3. Set your Roster row: Doing = `done`, Blocked? = `no`.
```

### `agents/<name>/NOTES.md` (agent-written)

The long form of the Roster row, for the UI and for the operator: the current task, what the agent tried, what it waits for and on whom, the next three steps. The agent rewrites it whenever its Roster row changes. Other agents never read it; they get the Roster row.

## Messages

`inbox/` holds short text messages, one file each: `<HHMMSS>-<from>-<to>.md`, where `to` is an agent name, `operator`, or `all`. First line is the subject.

Delivery:

- With the daemon: a new file addressed to a running agent becomes a **steer** message to that pi session (it enters after the agent's current turn and tool calls, so it never interrupts an edit mid-flight). Messages to an idle agent are prepended to its next prompt. Messages to `operator` show up in the UI and are also appended to the Log.
- By hand: the operator pastes the message into the target agent's terminal. Tolerable for two agents, which is why the daemon's first job is this.

Agents prefer the Log for status and messages for questions and hand-offs ("contract posted, you are unblocked"). Nothing important lives only in a message; decisions go to *Contracts*.

## Change propagation

The daemon watches `MISSION.md`, `agents/*/NOTES.md` and `inbox/`. On a change by agent A it sends the other running agents one debounced steer message (≤ 1 per 30 s per agent):

> MISSION.md changed by backend-api: Roster (own row), Contracts (+1), Log (+2). Re-read `.spinner/MISSION.md` before your next edit.

Agents that are idle get the same line at the top of their next prompt instead. The operator never gets steer messages; the UI shows a diff.

## Threads: `threads/<repo>-<pr>.md`

A *thread* is a GitHub review thread. The daemon renders one file per PR from GitHub whenever the threads change. Agents read it and act on it through the `thread_*` tools; nobody edits it by hand. Each thread carries the id the fixer agent needs to reply and resolve.

```markdown
# backend #412 · 2 open threads (2 bot, 0 human) · checks: green · review: none

## T1 · open · devin-ai-integration[bot] · src/refunds/workflow.ts:88
> The retry policy here is unbounded; a permanently failing Stripe call will
> retry forever. Consider maximumAttempts or a non-retryable error for 4xx.

## T2 · open · sonarqubecloud[bot] · src/refunds/workflow.ts:41
> Remove this unused import 'Duration'. (typescript:S1128)

## Resolved (7) · collapsed · `spinner threads s17 --all` to list
```

Fixer rules. The fixer's brief carries them and the tools enforce them:

1. For each open thread, do one of two things. Fix it and reply with one line that says what changed. Or reply with a one-line reason and flag it for the operator (`thread_flag`).
2. Do not skip a thread.
3. Resolve a thread only after its fix is pushed and the checks are green again.
4. With `threads.resolve_human: true` the agent answers and resolves human threads too. With `false`, the agent replies and leaves them open for the reviewer.
5. Flag a thread that asks a design question, disagrees with the approach, or touches something outside the session. Do not argue with it.
6. Make one commit per batch of fixes: `fix(review): address N review comments`, with the usual trailers.
7. Append one Log line per batch: `09:40 fixer: resolved T1, T2 on backend#412; T3 flagged (design question)`.
8. Do not wait for a review bot to come back. Bots re-review after a large push or after some time. New bot threads re-enter *fixing* at any stage.

## Lifecycle and pipeline stages

A session's `stage` is **derived** by the daemon from facts it collects (PR state, checks, review threads, merge-queue events, the operator's "verified locally" tick, the Slack post). Nobody sets it by hand, so the board is always true. A session with several PRs is at the earliest stage of its open PRs; the board shows per-PR detail underneath.

```
planned → building → bot-review → fixing → verifying → peer-review → addressing → approving → queued → merged → closed
                        ▲            │                                    │                      │ popped
                        └────────────┘  (new bot threads after any push)  └──────────────────────┘ (rebase, re-queue)
```

| Stage | Entered when | The daemon does | You do |
|---|---|---|---|
| **planned** | session created, no commits | — | write *Goal* / *Done when*, add agents |
| **building** | commits on the branch, no PR or a draft PR | tracks agents and the mission | review the plan; `spinner pr` when ready |
| **bot-review** | PR open; a configured review bot has not yet posted on it, or checks still pending | polls GitHub; notifies when the bot posts or checks finish | nothing. This is the wait you used to babysit. |
| **fixing** | any open bot thread, or checks red (at any later stage too: bots re-review after substantial pushes or after a while) | writes `threads/`; starts or steers the fixer (`spinner fix`, or automatically per `threads.autofix`); the agent pushes and resolves | skim the fix commits |
| **verifying** | no open threads, checks green, head not yet verified | `spinner up` if the stack is down; surfaces the previews | test it in the previews; tick **verified** (`spinner verify`) |
| **peer-review** | verified; the PR set is posted to Slack; no reviewer activity yet | posts only on your command; then watches replies to the Slack post, mentions and GitHub reviews; notifies on activity; marks `stale` after N quiet hours | nothing until a reviewer responds; nudge if stale |
| **addressing** | human threads open, or `changes_requested` | updates `threads/`; runs the fixer (with `threads.resolve_human: true` the agent answers, fixes and resolves human threads too); threads it flagged show up in `needs_human` | decide the flagged ones |
| **approving** | threads resolved, checks green; the configured approval check is still waiting. The rule comes from `approval_policy` by PR author (example: a human-authored PR needs one peer approval; a bot-authored PR needs the peer **and** the person who instructed the bot) | tracks `approvals.required` vs. received per PR; `needs_human: "approve admin#98"` the moment a PR whose rule includes you has its peer approval and lacks yours | `spinner approve` (your GitHub approval, as you), or nudge the peer |
| **queued** | approval check passed and enqueued (`spinner land`) | polls the queue entry; on removal sets `queue: popped`, has an agent rebase onto `base`, waits for green checks, re-enqueues, notifies | nothing, unless the rebase hits a conflict that needs a decision |
| **merged** | every PR merged into `base` | notifies; `needs_human: "close or reset"` | `spinner close` or `spinner reset` |
| **closed** | torn down and archived | — | — |

With a GitHub merge queue, a PR can be enqueued as soon as its checks pass, the approval check included. A pop-out then means a conflict or a failure against newer `base`, which is what the re-queue loop handles.

`needs_human` is the one line the board shows per session: `null` when nothing is waiting on you, otherwise the single next action ("verify locally", "approve backend#412", "T3 on backend#412 flagged: design question", "popped out of queue: conflict in migrations/"). The board sorts sessions by it, so the top of the list is always your to-do.

Commands and what they change:

- **new**: session directory, `session.yaml`, `MISSION.md` from template, worktrees on `base`, branch created in each repo.
- **up / down**: start or stop the stack. Worktrees and agents are untouched.
- **pr**: for each repo with commits ahead of `base`, push and `gh pr create` with a body generated from *Goal*, *Done when* and the Log. PR numbers go into `session.yaml` and the Log. Stage becomes *bot-review*.
- **fix**: start (or steer) the fixer agent on every open thread in `threads/`. Allowed in *fixing* and *addressing*. `threads.autofix` decides what the daemon starts without asking: `all` (bot and human threads alike), `bots`, or `off`.
- **verify**: records your local test (`verified_locally: true`, the head SHA per repo, who, when, an optional note). Required before *post*. Any later push to a branch clears it, so you re-verify what actually ships.
- **post**: composes the Slack message (one post per session: the PR links as a set, the *Goal* in one line, a tagged reviewer if you name one) and shows it; posts on confirmation (`--yes` to skip). Stores the post URL in `slack_post`. The daemon never posts to Slack on its own initiative; it only reads the replies afterwards.
- **approve**: submits your approving review through `gh pr review --approve`, as you, after showing you what you are approving (head SHA, diff stat, open threads = 0). Needed only for PRs whose approval rule includes you, such as bot-authored PRs you adopted. PRs that Spinner opens are authored by you, and GitHub does not let an author approve (see [PR authorship](ARCHITECTURE.md#pr-authorship)).
- **land**: requires every PR's approval check passing, all other checks green, no open threads; enqueues each PR in the GitHub merge queue with `expectedHeadOid`; watches until merged; handles pop-outs as above.
- **reset**: after merge, start another round on the same session: new branch from fresh `base`, worktrees fast-forwarded, stack recreated, DB re-cloned, pipeline facts cleared. `MISSION.md` keeps its history under a `## Previous rounds` heading; agent transcripts stay resumable.
- **close**: stop the stack, drop the DB, remove the worktrees (branches stay in the repos), move the session directory to `~/.spinner/archive/`.

## Commit and branch conventions

- Branch name is identical across repos: `feat/<slug>` (or `fix/`), from `session.yaml`.
- Agents commit their own work, small and often. The daemon's `git` wrapper adds trailers so history stays attributable: `Spinner-Session: s17` and `Spinner-Agent: backend-api`.
- Repos with no commits ahead of `base` stay on `base` and get no PR.
- Never force-push a session branch; `reset` makes a new branch instead.

## What the pi extension provides (M2)

So that agents follow the protocol without being told every turn, `spinnerd` loads a pi extension into each agent session:

- **System prompt section**: session id, hostnames, the agent's `BRIEF.md`, the full `MISSION.md`, and a one-line digest per other agent (`admin-ui: blocked on /refunds`).
- **Tools**: `mission_roster(doing, blocked)`, `mission_log(text)`, `mission_contract(text)`, `mission_question(text)`, `message(to, text)`, `stack(show|logs|restart <service>)`, `pr(show)`, and for the fixer role `thread_list(pr?)`, `thread_reply(thread, text)`, `thread_resolve(thread)`, `thread_flag(thread, reason)`. Tool writes are serialized by the daemon, so no two agents edit `MISSION.md` at the same moment; `thread_resolve` refuses human threads when `threads.resolve_human` is off, and always refuses a thread that has not been replied to.
- **Hooks**: a `beforeTool` guard that warns when an `edit`/`write` targets a path outside the agent's owned globs, and asks it to log first.

Until then, the brief carries these instructions, and the operator serializes by running only two or three agents at once.
