# s006 · Daemon lifecycle and the newcomer path

## Goal
Close M3. A new user clones the repo, follows the README, and reaches a running UI on their own stack in under an hour, without this chat. That needs the daemon to start and stop like a tool (`spinner daemon start|stop|status|logs`, launch at login on macOS), the binaries and tokens it uses to come from one settings file, the README to show the path, and CI to run what the laptop runs. One agent.

## Done when
- [x] `spinner daemon start` starts the daemon in the background with its log under `~/.spinner/`, `status` says if it runs and on which build, `stop` stops it, `logs` tails; `start` twice is a no-op; a stale pid file is handled
- [x] `spinner daemon install` writes a macOS launch agent (`~/Library/LaunchAgents/dev.spinner.daemon.plist`) that starts the daemon at login with the user's environment; `uninstall` removes it
- [x] `~/.spinner/config.yaml` holds the non-secret settings the daemon needs (`pi_bin`, `port`, `default_model`, `slack.channel`); secrets still come from the environment, and the launch agent reads them from `~/.spinner/env` (mode 600, documented, never created by Spinner with a value)
- [x] `spinner doctor` checks: `~/.spinner` outside git, Docker up, `gh` logged in, `pi` found, Node version, the proxy and Postgres state, the token present or absent; exit 1 with a list on failure
- [x] README shows the newcomer path start to finish on `examples/sample-stack`, timed by the agent in a fresh clone under a fresh `SPINNER_HOME`; the time is written into STATUS
- [x] CI runs `examples/sample-stack` through `new → up → close` in a job with Docker, and runs the daemon's stack and pipeline tests on Linux
- [x] `pnpm -r build && pnpm -r test && pnpm lint` and `doc-metrics --fail` green; Log tells the story
