# s011 · The operator agent: Spinner talks back

## Goal
Today the operator runs Spinner's own build from a terminal outside the app: a chat with a parent agent that writes missions, starts subagents, relays messages and reports. After this session that chat lives inside Spinner. An operator agent, one per home, always available, sits in its own tab. The operator pastes a PR or a ticket and says what he wants; the agent creates the session, attaches the project, writes the mission and the briefs, starts the agents, and tells him where to click. It is woken by the daemon's events, so it relays and asks the way the parent chat does. Two agents: `engine` (daemon, extension, protocol, cli) and `ui`.

## Done when
- [ ] The daemon hosts one operator agent per home under `~/.spinner/operator/` (its pi transcript, `BRIEF.md`, `inbox/`): a tty pi in the home directory, started with the daemon when `settings.operator.enabled` is true (the default), resumed on restart like a session agent, stopped with `POST /operator/stop`, started with `POST /operator/start`
- [ ] The extension's role `operator` adds the tools `session_new`, `session_adopt`, `session_attach`, `session_list`, `session_show`, `mission_write` (one section of a named session), `brief_write`, `agent_add`, `agent_steer`, `inbox_send`, and keeps `stack` and `pr`; every tool goes through the daemon's routes and is logged in the session's Log
- [ ] The operator agent is woken by events: `needs_human` set, `agent.settled`, `agent.exited`, `job.finished` with state `failed`, an inbox message addressed to `operator`; each arrives as one notice in its terminal with the session and the fact, batched per second so a burst is one notice
- [ ] The operator agent's brief (`packages/daemon/src/store/operator-brief.ts`, written once, editable) says: what Spinner is, how a session is shaped, how to turn a request into a mission and briefs (the shape in `examples/sessions/`), that it starts agents without asking, and that it never pushes, posts, approves, lands or closes without the operator's word; product calls become Open questions and `needs_human`
- [ ] The UI has an operator tab: an icon in the activity bar above the gear; it opens the operator's terminal full width in the middle (the agents pane's terminal component, pointed at `/operator/tty`), with `stop`/`resume` and a line that says what it is waiting on; a notice in the context bar when the operator agent is not running
- [ ] E2e on a scratch daemon with the real pi: the operator agent receives "start a session for the sample stack named Refund flow with one agent `backend` that adds a health endpoint", creates the session, attaches the sample project, writes a mission with a Goal and three Plan items, writes the brief, starts `backend`; the agent's `agent.settled` reaches the operator agent as a notice
- [ ] `pnpm -r build && pnpm -r test && pnpm lint` and `doc-metrics --fail` green; `docs/ARCHITECTURE.md` gains "The operator agent"; `docs/DAEMON_API.md` lists the routes; Log tells the story

## Contracts & decisions
- 2026-10-30 the operator: one operator agent per home; it has no session, no worktree and no stack; its cwd is the home directory; it reads and writes sessions only through the daemon.
- 2026-10-30 the operator: the operator agent starts agents without asking. It never pushes, posts, approves, lands, resets or closes without the operator's word; the extension refuses those calls in the operator role.
- 2026-10-30 the operator: notices come through the extension channel of s011 (`notify`), batched per second; a notice is text, with the session dir first.
- 2026-10-30 the operator: the operator agent's model is `settings.operator.model`, else `settings.default_model`, else the daemon's default.
- 22:26 engine: **operator contract** (protocol types in `packages/protocol/src/{api,events,theme,extension}.ts`, commit `engine: protocol types for the operator agent`).
  - Routes: `GET /operator` → `OperatorResponse { operator: OperatorView }`. `POST /operator/start` → 200 `OperatorResponse`, 409 while it runs, 500 when pi fails to start. `POST /operator/stop` → 200 `OperatorResponse`, 409 when it does not run. `POST /operator/prompt` and `POST /operator/steer` → body `AgentMessageRequest { text }`, 200 `AgentCommandResponse`, 409 `{ error }` when not running. `GET /operator/tty` (`OPERATOR_TTY_PATH`) → WebSocket with the same frames as `tty_path(dir, name)` (binary both ways, text `{resize}` up, text `{exit}` down), plain 404 before the upgrade while the agent is stopped. The extension's routes `POST /operator/hello`, `GET /operator/commands`, `POST /operator/events` mirror the per-agent ones.
  - `OperatorView { enabled, process: "idle"|"running"|"exited", pid, model, dir, waiting_on: "operator"|"model"|"start", last_notice: { ts, text } | null, notices_pending }`. `waiting_on` is `operator` when idle (a person types in its terminal), `model` while a turn runs, `start` when no process runs.
  - Event `operator.updated { ts, session: null, data: OperatorView }` on start, stop, exit, turn start, turn end and each delivered notice. The UI's exhaustive switch in `packages/ui/src/describe.ts` needs a case for it (ui).
  - Notice: one `notify` through the extension channel per second at most; text is one line per event, each `<session dir>: <fact>`; events are `needs_human` set (`session.updated` where `needs_human` goes from null to text), `agent.settled`, `agent.exited`, `job.finished` with `ok: false`, `inbox.message` to `operator`. Queue bound 100; the oldest are dropped and the notice's first line says how many. Notices wait while the agent is stopped and go out on start.
  - `settings.operator?: { enabled?: boolean (default true), model?: string }`; `PUT /settings` validates it like `agents`.
  - Tools (role `operator`, `SPINNER_ROLE=operator`, `SPINNER_SESSION_DIR=<home>/operator`): `session_new { title, project?, slug? }`, `session_adopt { urls, project?, title? }`, `session_attach { session, project }`, `session_list {}`, `session_show { session }`, `mission_write { session, section: goal|done_when|plan|contracts|open_questions|log, text }` (goal and done_when replace; the rest append), `brief_write { session, agent, text }` (new route `PUT /sessions/:dir/agents/:name/brief`, body `{ brief }`), `agent_add { session, name, brief?, repo?, model? }`, `agent_steer { session, agent, text }`, `inbox_send { session, to, subject, text }`; `stack` and `pr` gain an optional `session` the operator role needs. `ExtensionToolSpec.role` became `roles: ExtensionRole[]`. In the operator role a `bash` call that runs `spinner pr|post|approve|land|reset|close`, `git push` or `gh pr create|merge|review` is blocked with "the operator must do it".
- 23:11 engine: **contract addendum** (commit 7418487): `OperatorView.ready: boolean`, true once the extension inside pi posted `hello` (a prompt or a notice reaches it); `operator.updated` fires on it.
