# s016 · The review lead: one review in one voice

## Goal
The swarm of s015 posts one set of inline comments per model, as `review-blast` did. The operator's better review process is the `pr-review` skill: three read-only reviewers return a verdict, a lead writes the operator a plain-language briefing while they run, then reconciles the verdicts into one review in one voice, shows the draft, and posts only when the operator says so. After this session a review session runs that process: a `lead` agent with the skill's role, reviewers that write verdict files and never post, the briefing and the draft in the review pane, and `post` as the operator's click. The per-model posting goes away. Two agents: `engine` and `ui`.

## Done when
- [ ] A review session starts a `lead` agent at creation (model `settings.default_model`), with a brief from the `pr-review` skill: read the PR and the repository, write the briefing first through `review_briefing`, then wait for the verdicts, apply lead judgment, and write the draft through `review_draft`; never post, never edit files, never name a model in any GitHub text
- [ ] The swarm starts the reviewers as before (one per `settings.review.models`, states `queued|reading|done|failed`) with the `reviewer` role's brief and the skill's rulebook: read only, no posting, end with the `VERDICT` contract; the daemon saves each verdict to `artifacts/reviews/<model-slug>.md` from the transcript on settle and notifies the lead through the extension channel when the last one lands
- [ ] `review_briefing { markdown }` writes `artifacts/briefing.md`; `review_draft { event, body, comments: [{ path, line, body }] }` validates the comment format (one severity label first, lines in the diff) and writes `artifacts/review-draft.json`, sets `needs_human` with a `review_draft` reason
- [ ] `POST /sessions/:dir/review/post` posts the draft as one PR review at the head SHA through the operator's `gh` (`APPROVE` or `COMMENT` as drafted; `APPROVE` rejected for the author's own PR falls back to `COMMENT` and says so); `PUT /sessions/:dir/review/draft` saves the operator's edits; `DELETE` drops it; the posted review's URL lands in `session.yaml` and the Log
- [ ] `SessionView.review` carries `briefing: boolean`, `draft: { event, body, comments } | null`, `posted_url`; `review.updated` on each change
- [ ] The review pane shows the briefing as markdown as soon as it exists, then the draft: the event and the summary body, each line comment as `path:line` with its text editable, `post`, `drop`; `post` asks once in place; after posting, the review URL; the swarm chips read `done` instead of `posted`
- [ ] `review` on an ordinary session runs the same process; its lead is the session's existing lead
- [ ] E2e on a scratch daemon with the real pi and one reviewer model on the sandbox PR: the briefing appears, the verdict file appears, the draft appears with `needs_human`, `post` posts one review and the URL shows
- [ ] Checks green; `ARCHITECTURE.md` "Reviews" and `DAEMON_API.md` updated

- 14:07 engine (Plan 1, the review lead contract; protocol types in `packages/protocol/src/{session,api,extension}.ts`, ui build touches `packages/ui/src/review.ts`, `remote.ts`, `describe.ts`, `styles.css`):
  - **States.** `SwarmState = queued | reading | done | failed`. `posted` is gone. `done` = the verdict file is written and the reviewer's pi is stopped. `failed` = the reviewer settled without a `VERDICT:` block, or exited. The swarm chips read `done`.
  - **Files in the session directory.** `artifacts/briefing.md` (the lead's briefing, markdown). `artifacts/reviews/<model-slug>.md` (one verdict per reviewer: the reviewer's last assistant text, verbatim). `artifacts/review-draft.json` (`ReviewDraft`). After `post`: `artifacts/review-posted.json` (the draft as posted plus `url`), and the draft file is removed.
  - **Types.** `ReviewEvent = "APPROVE" | "COMMENT"`. `ReviewDraftComment { path: string; line: number; body: string }`. `ReviewDraft { event: ReviewEvent; body: string; comments: ReviewDraftComment[] }`. `ReviewFields` gains `briefing: boolean`, `draft: ReviewDraft | null`, `posted_url: string | null` (the daemon always sets the three). `session.yaml` `review` gains `posted_url?: string | null` and `draft?: boolean` (true while the draft file exists; the tracker reads it). `REVIEW_DRAFT_NEEDS_HUMAN = "post or drop the review draft"` is the `needs_human` text while a draft exists (it wins over the pipeline's own text, like a diff comment). `LEAD_NAME = "lead"`.
  - **Routes.** `GET /sessions/:dir/review/briefing` → `text/markdown`, 404 before it exists. `PUT /sessions/:dir/review/briefing { markdown }` → `{ ok: true }` (the lead's tool). `PUT /sessions/:dir/review/draft` body `ReviewDraft` → `{ draft: ReviewDraft }` after validation (the lead's tool and the operator's edits take the same route); 400 with `{ error }` listing every fault: `event` not `APPROVE|COMMENT`, a comment `body` that does not start with `BLOCKING:`, `BUG:`, `NIT:` or `SUPER NIT:`, a `path:line` that is not on the right side of the PR diff (`gh api .../pulls/:n/files`, added and context lines). `DELETE /sessions/:dir/review/draft` → `{ ok: true }`, 404 without a draft. `POST /sessions/:dir/review/post` → `ReviewPostResponse { url: string; event: ReviewEvent; fell_back: boolean }`; 409 without a draft or with one already posted at this head, 502 with `{ error }` when GitHub refuses. All four answer at once (no job). The post goes through `gh api repos/:owner/:repo/pulls/:n/reviews` with `commit_id` = the PR head, `event`, `body`, `comments[]` with `side: RIGHT`; an `APPROVE` GitHub rejects for the author's own PR is reposted as `COMMENT` with `fell_back: true`. The URL lands in `session.yaml` `review.posted_url` and in one Log line; `needs_human` clears; `review.updated` follows each of the four.
  - **Events.** No new event type. `review.updated { data: ReviewFields }` on each change of briefing, draft, posted_url or a swarm state, as in s015.
  - **Tools (role `lead`).** `review_briefing { markdown }` → `PUT .../review/briefing`. `review_draft { event, body, comments }` → `PUT .../review/draft`; `comments` is a JSON array text of `{ path, line, body }`. A bad draft returns the errors to the lead and writes nothing.
  - **Who starts what.** `POST /reviews` creates the session, starts the agent `lead` (model `settings.default_model`, brief from the `pr-review` skill, cwd the PR worktree) with the PR URL as its first message, then starts the swarm, as one job. `POST /sessions/:dir/review` starts (or restarts) the swarm alone: on a review session a second round, on an ordinary session the same process with the session's existing `lead` (a notice with the lead-judgment rules reaches it when the last verdict lands; without a running `lead` the notice waits for its next prompt). The daemon never posts.

E2e adds: no `/tty` upgrade for the review session's agents, and a reviewer with a bad model reports `failed` with its reason.

- 14:24 engine (not blocking; decided with a default, change it if you want): (a) `POST /reviews` starts the lead **and** the swarm on the paste (the paste is the request; the skill launches the ensemble in the same turn as the briefing). Before s016 the operator clicked `review` after the paste. The click still exists for a second round. (b) The post of a review session's PR passes the `write_repos` guard with the PR's own repo added for `kind: review` sessions only (they have no project, so the list is empty); an ordinary session's PR must be on its project's `write_repos`, as `approve` requires.
