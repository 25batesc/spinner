## Open questions
- engine, 1.9 (finding, built a variant): the design's adapter frontmatter line `extensions: []` does not mean "no extensions" in pi-subagents 0.84.0. Its parser (`src/agents/frontmatter.js` `parseUnquotedList`) reads `[]` as one extension named `[]`. Its docs (`docs/agents.md`, "Extension loading") name `extensions:` with an empty value as "no extensions". The adapter writes `extensions:`. The design text of T2 and 1.9 should say so.
- engine, version (finding): the installed pi-subagents is 0.84.0, not 0.83.0 as the design cites. The three variables exist in 0.84.0 at the cited files. The evidence (1.27) records 0.84.0.
- engine, pre-existing (not built, not blocking): `packages/daemon/src/pipeline/reviews.test.ts` "makes a review session" expects `pi is not on PATH`; on a machine with pi on PATH it fails, and before 7ce3a6b it started real reviewers with the operator's credentials. With 7ce3a6b the daemon tests set `PI_CODING_AGENT_DIR` to a missing directory, so pi starts without credentials and fails with a different reason; the test still fails. A fix would set `SPINNER_PI` to a missing path in that test. Operator: build that fix in this session, or leave it?
- ui, 1.36 and 1.39 (finding, not blocking): 1.39 has the fixture serve only `ready`, and 1.36 shows the `fetch` button only for `absent` or `failed`. So no driver clicks the button; the flow `about-egm` posts `POST /egm/fetch` itself and checks the reload. A fixture start state (for example `SPINNER_FIXTURE_EGM=absent`) would let the driver click it. Add it in build session 2, or leave it?
- ui, 1.35 (finding, built): the design names no change to `packages/ui/vite.config.ts`, but its dev proxy lists each daemon path. Without `/egm` in that list, `GET /egm` in `pnpm --filter ui dev` answers vite's `index.html`. ebeabd9 adds `/egm`. A later entry that adds a top-level route (not under `/sessions`) must name this file.
- engine, 1.22 (finding, not built): a daemon started from inside a pi session that is itself a pi-subagents child inherits `PI_SUBAGENT_CHILD=1` and passes it to every agent it spawns (`pi-rpc.ts` and `tty-harness.ts` spread `process.env`). With 1.22 the Spinner extension then stays off for every agent: no tools, no hello. The first e2e run hit this, because this agent is a pi-subagents child. The driver now drops the inherited `PI_*` variables (except `PI_CODING_AGENT_DIR`) from the scratch daemon's environment. A product fix would delete `PI_SUBAGENT_CHILD` from the spawn environment in `pi_spawn_plan`. Build it in session 2, or leave it?
- engine, T5 and P8 (finding): the lead chose foreground runs (`"async": false`) for the P2 probes. pi-subagents writes no `async-subagent-runs/*/status.json` for a foreground run; its files are `<session>/agents/lead/pi/subagent-artifacts/<runId>_<agent>_<step>_{meta.json,output.md,transcript.jsonl,input.md}`. The GoldfishWatcher of T5 (session 4) reads only status files, so it would not see a foreground Goldfish, and P8 as written reads only status files. The driver also reads the `meta.json` agents for P8.
- engine, 1.34 (blocked on a guard, not on the design): folding `docs/designs/README.md` into `SITEMAP.md` needs `git rm docs/designs/README.md`. The operator's damage-control extension refused that command ("rm on protected file (README.md)"), and I did not retry. SITEMAP.md exists (50040d3) with the README text and the table. Operator: remove `docs/designs/README.md` by hand, or keep it? `tools/doc-metrics.py` line 130 cites `docs/designs/README.md` in a comment; `tools/` is not mine.
